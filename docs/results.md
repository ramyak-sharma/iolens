## V4: overhead

Environment: kernel 6.10.14-linuxkit, aarch64, 8 CPUs, 7.7 GiB, 2026-10-22T16:45:37Z. Device: `loop-on-tmpfs`.

**Not the reference setup.** null_blk was not available, so this used a loop device on tmpfs. It is still a near zero latency device (about 1M IOPS here), so it is close to the worst case, but the number should be redone on null_blk in the Lima VM.

| | mean IOPS | std dev |
| --- | --- | --- |
| iolens off | 991680 | 77085 |
| iolens on | 873956 | 10136 |

IOPS loss: **11.9%** (target at most 5%, missed).

Per event cost from kernel BPF stats: complete 221 ns, insert 3590 ns, issue 255 ns. Insert only fires when a request goes through the scheduler, so it is rare on this device and its average is noisy. Enabling BPF stats itself adds a little per event.

What that means on a real disk: issue plus complete is about 476 ns per request. A disk request of 100 us (fast NVMe) would pay 0.48% extra, a 1 ms request 0.048%.

Agent while running: 0.05% of one core, 42 MiB RSS.

Most likely cause of the miss: all 4 fio jobs complete I/O for the same (cgroup, device, op) key, so the atomic adds on that one `hists` entry bounce a cache line between CPUs. That is the known cost from the spec; the per-CPU variant is the next step.
